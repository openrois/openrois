# Fixtures

Test data that the Python, TypeScript and C# interface packages all read, so the three cannot
drift apart.

| File | Holds | Comes from |
|------|-------|------------|
| `wire.json` | `{kind, method, body}`: real messages, each parsed into its model and written back | Generated by `testing/conformance/capture.py`. Do not edit it by hand |
| `conditions.json` | `{builder, args, expected}`: the condition builders, with `args` as positional arguments and an identifier as `{authority, code}` | Written by hand |
| `values.json` | `{data_type, value, text}`: `encode_value(data_type, value)` gives `text`, and `decode_value(data_type, text)` gives `value` | Written by hand |
| `value-edges.json` | The edges that `values.json` cannot hold, and the `all_of` cases the languages differ on, in the lists below | Written by hand |

Every body in `wire.json` holds all the fields of its model, with null for an unset one. The
script fails unless the file also holds a value in each field, and each enumerator, that `WANTED`
in `capture.py` names, such as command arguments and the ways a command ends. Builder names are
the Python names. The `text` of `values.json` is the exact output of Python's `json.dumps`, so a
float always has a fraction or an exponent (`2.0`, `1e-05`, `1e+16`), an array has a space after
each comma, and a non-ASCII character stays as it is.

`values.json` holds only canonical values, which survive both directions, so it cannot see how a
language treats anything else. `value-edges.json` is one object, read by the three test suites, and
by `testing/unity-harness` for every list except `conditions`, with these lists:

| List | Holds | A language passes when |
|------|-------|------------------------|
| `refused` | `{data_type, text}` | `decode_value` refuses `text` |
| `decoded` | `{data_type, text, value}` | `decode_value` reads the non-canonical `text` as `value` |
| `encoded` | `{data_type, value_text, text}` | `encode_value` writes the value in `value_text` as `text` |
| `doubles` | `{bits, text}` | The double with these bits writes `text`, and `text` reads as these bits |
| `models` | `{name, kind, method, refused, body}` | The catalog model of `kind` and `method` refuses or reads `body`, as in `wire.json` |
| `conditions` | `{name, builder, args, expected}` | The builder gives `expected` from `args`, as in `conditions.json`. These cases show what each language counts as blank |
| `exceptions` | `{language, why, cases}` | See below |

JSON has no form for some values, so they stand as text. A float in the `value` column of `decoded`
is a JSON number, or the text `NaN`, `Infinity`, `-Infinity` or `-0.0`. A `value_text` is a JSON
value that may also hold those three names: an integer in it is an integer passed to a float type,
such as `9007199254740995`, which writes `9007199254740996.0`. In `doubles`, `bits` is the
big-endian IEEE 754 form in hexadecimal, so a runtime that reads decimal text inexactly cannot hide
a fault. It holds exact powers of two, the largest doubles, and random doubles that broke the text
and parsing of the Mono and IL2CPP runtimes.

An entry of `exceptions` records one accepted difference: `language` is the one that differs, `why`
says why, and each item of `cases` names a case by its `list` and the identifying fields of that
list. A listed case is skipped for that language only, and the others still run it. The test
suites also fail on a listed case that a language has stopped differing on, so a fixed difference
has to leave the file. A difference that is not accepted does not belong here: fix the language.
